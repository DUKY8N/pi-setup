다음 범위의 코드 네이밍을 리뷰해.

검토 범위:
$ARGUMENTS

검토 범위가 비어 있다면:
- 먼저 현재 대화나 에디터 컨텍스트에서 검토 대상을 추론해.
- 가능하다면 `git status`와 diff를 기준으로 최근 변경된 코드의 네이밍을 우선 검토해.
- 검토 대상을 특정할 수 없으면, 어떤 범위를 제공해야 하는지 짧게 안내해.

중요 규칙:
- 코드는 수정하지 마.
- 네이밍 품질 평가와 개선 제안만 제공해.
- 맥락이 부족한 경우에는 가정을 짧게 명시해.

검토 대상:
- 변수, 함수, 메서드, 클래스, 파라미터, 상수
- 타입, 인터페이스, enum
- 파일명, 모듈명, 패키지명, 네임스페이스
- public API와 private API 이름

검토 기준:
- 해당 언어의 일반적인 네이밍 컨벤션을 따르는지
- 이름만으로 역할, 의도, 책임이 드러나는지
- Boolean 이름이 자연스럽게 읽히는지
- 함수와 메서드 이름이 동작, 반환값, 부수 효과를 잘 드러내는지
- 클래스, 타입, 인터페이스, enum 이름이 관용적인지
- 도메인 용어가 일관되게 쓰이는지
- 영어 표현이 영어 원어민 개발자에게 자연스럽고 관용적인지
- 약어, 축약어, 접두사, 접미사가 일관되게 쓰이는지

출력 형식:

# 전체 평가

네이밍 품질, 언어별 관례 적합성, 도메인 용어 일관성을 간단히 평가해.

# 개선 제안

| 위치 | 현재 이름 | 추천 이름 | 이유 |
|---|---|---|---|

# 네이밍 일관성 제안

반복적으로 보이는 네이밍 패턴, 불일치, 도메인 용어 문제, 컨벤션 위반을 정리해.
